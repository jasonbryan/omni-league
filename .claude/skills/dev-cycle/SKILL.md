name: dev-cycle
description: Runs the Omni League development cycle by dispatching role agents. Use when the owner asks to build a feature, fix a bug, plan a requirement, work an issue, continue the backlog, or deploy.
---

The main session is the **orchestrator**. It dispatches the role agents in `.claude/agents/`, moves issue labels, merges every PR outside the owner-merge scope, and reports to the owner per milestone. The owner merges only gate PRs and changes to secrets or security policy (`docs/process/dev-cycle.md`, Who merges); the orchestrator merges those only on the owner's chat instruction. It does not plan, design, write feature code, test, or review itself; each of those goes to its role agent, so every phase gets a fresh, independent context. It does run the batch run and its bisect itself (`docs/process/dev-cycle.md`, Batch run), as it watches `ci`, and dispatches `implementer` for any fix or revert.

Read `docs/process/dev-cycle.md` first. It defines the phases, the done-criteria, the labels, and the loop caps used below.

## Steps

1. **Sync.** `git fetch` and fast-forward `main`. List open issues with their labels (`gh issue list --state open --json number,title,labels`) and open PRs (`gh pr list --json number,title,labels,headRefName`). Check which gate PRs the owner has merged since the last run, and move their issues to `status:ready`.

2. **Choose work.** If the owner gave a new requirement, start at step 3. If the owner named an issue, work that issue. Otherwise pick the **frontier**: `status:ready` issues with no open `Blocked by` issue, oldest first. Run independent frontier issues in parallel, but only one issue at a time that touches `convex/schema.ts` or shared design tokens. Start no new frontier issue while 5 or more non-Dependabot PRs are open: first move each open PR to its next phase. Not counted: PRs labelled `gate:*` or carrying `Needs owner: merge`, and PRs whose linked issue is labelled `status:blocked`. Exempt: the fix-forward or revert issue during a batch-run regression, and work the owner names in chat. Count with `gh pr list --state open --json number,author,labels`, excluding author `app/dependabot` and those PRs (process doc, Parallel work).

3. **Plan.** Dispatch `planner` with the requirement. Then, for each new issue, dispatch `plan-reviewer`. On `CHANGES`, send the edits back to `planner`; after two rounds without `APPROVE`, label `status:blocked` and add the issue to the owner report.

4. **Gates.** For an approved issue with gate labels, set `status:needs-approval` and dispatch `planner` for an ADR (`gate:technology`). The issue now waits for the owner; move on to other work. With no gates, set `status:ready`. New screens and visible changes need no gate; dispatch `designer` only when the owner asks for a mockup.

5. **Implement.** Set `status:in-progress` and dispatch `implementer` with `isolation: "worktree"`, passing the issue number. If it reports a need for new technology, send the issue back to step 4.

6. **Test, then review.** Classify the PR's head SHA by Low-risk PRs in Phase 5 of the process doc. A low-risk PR gets the comment `Test: skipped (low-risk: <tests and docs only | dependency bump | Dependabot github-actions>) at <head SHA>` and goes to `pr-reviewer` without `tester`. A fix push on a PR that already has `Test: PASS` is also low-risk when the cumulative diff from the last `Test: PASS` SHA to the new head is only safe changes (comment-only in code files, `*.md` docs, test titles): post `Test: skipped (low-risk fix push: <reason>) at <sha>`, with all local checks plus the own specs run on that exact head as the stand-in (process doc, Low-risk PRs). Otherwise dispatch `tester` with the PR number. On `FAIL`, dispatch `implementer` to fix, then `tester` again. On `PASS`, dispatch `pr-reviewer`. On `CHANGES`, run `implementer` → `tester` → `pr-reviewer` again, and re-classify after each push: a push that adds a file outside the low-risk rules brings `tester` back, and a push that keeps the PR low-risk gets a new `Test: skipped` record for the new head SHA instead of `tester`. A reviewer whose only remaining findings are safe changes may post `Review: APPROVE (fix before merge: <n>)` with each fix as `path:line` and its exact old and new text. Dispatch `implementer` to apply exactly those replacements, check that the fix diff is exactly the listed replacements, post `Fix before merge: applied as listed at <sha>`, and merge without another review round; anything else in the diff goes back to review. That approval is not a round. After three rounds, label `status:blocked` and report.

7. **Merge.** When the merge conditions in Phase 7 of the process doc all hold, follow its five steps, one PR at a time: update the branch from `main` while still draft, keeping `PASS`, a `Test: skipped` record, and `APPROVE` only when the PR's own changes are unchanged (record the old head and merge-base before `gh pr update-branch`, run the `diff` on the new head, check `convex/_generated/`, and post `Update: own changes unchanged, old <old head sha>, new <new head sha>`; process doc, Phase 7 step 1); `gh pr ready <n>`; find the head's CI run with `gh run list --workflow CI --commit <head sha> --json databaseId,status,conclusion,createdAt`, take the newest, `gh run watch <id>`, and read the `ci` job's `conclusion` from `gh run view <id> --json jobs`: `ci` passes only on `success`, and `cancelled`, `skipping`, or a missing run is not a pass; `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>`. If `ci` fails, run `gh pr ready <n> --undo` and send it back to `implementer`. Until #12 adds `ci`, merge on `PASS` and `APPROVE` with a one-line merge note (`Merged; CI waived until #12`). The orchestrator never merges a PR carrying any `gate:*` label, or one that changes secrets or security policy (the owner-merge scope in the process doc, Who merges), unless the owner told it in chat to merge that specific PR; it then comments the owner's words on the PR, quoted exactly, before merging. Every other reviewed PR, including process-doc, `.claude/`, and mockup PRs, it merges itself. `APPROVE (fix before merge)` on the previous head, plus the `Fix before merge: applied as listed at <sha>` record, counts as `APPROVE` on the latest commit.

8. **Batch run, then deploy.** After the 5th merge since the SHA the last batch run tested, before each milestone report, and before a release PR, run the batch run on the `main` head (process doc, Batch run): a local `npm run e2e` in a worktree detached at `origin/main`, or `gh workflow run E2E --ref main` when the local run cannot complete. Skip it when every PR in the batch had ci scope `docs`. On a regression, hold merges, bisect, open the `type:bug` issue, and dispatch `implementer` as that section says. After a green or skipped batch run, dispatch `deployer` for preview/staging with the batch SHA (process doc, Batch run). Production goes through the deployer's `gate:production` release request.

9. **Report.** Report per milestone (a feature merged and live on staging, with its staging link; a release; a set of issues that finished together), not per step. Report immediately, outside that cadence, only when the owner must act: a gate PR or a secrets or security-policy PR waiting to be merged, a `status:blocked` question, or a budget or access problem. Each report is short, one line per item, following `AGENTS.md` (Writing on GitHub):
   - **Needs the owner:** gate PRs and secrets or security-policy PRs awaiting the owner's merge (with links), and `status:blocked` questions, each with the recommended answer.
   - **Done:** merged PRs and deployments, and the batch run result (`PASS` or `FAIL`, with the SHA it tested).
   - **In flight:** issues still moving, and their phase.

**Done when** every issue picked in step 2 is merged, waiting on the owner, or blocked with a question in the report.

## Dispatching

Give each role agent the issue or PR number, the phase, and any feedback it must act on. Each test, review, or fix round dispatches a new role agent, briefed with references only (the issue, the PR, the comment to act on). An existing agent is resumed (`SendMessage`) only to finish its own unfinished round, for example after an interruption or usage limit. Agents read GitHub themselves, so pass references, not copies of the issue. Agent reports are not shown to the owner; relay what matters in step 9.

### Model and effort

Each agent's frontmatter sets its default `model` and `effort` (table in [dev cycle, Roles](../../../docs/process/dev-cycle.md#model-and-effort)). The owner authorizes the orchestrator to override them per dispatch with the Agent tool's `model` and `effort` parameters, by these rules:

- **Mechanical or docs-only tasks** (label edits, applying a reviewer's exact wording, glossary entries): `sonnet` or `haiku`, `low` or `medium`.
- **Complex implementation or testing** (concurrency, SSR/hydration, cross-cutting infra): `implementer` and `tester` escalate to `opus`, `high`.
- **Security, payments, auth, and server-rendering work:** at least `opus`, `high`, in every role; the hardest of these may use `fable`, `xhigh`.
- **Small rounds:** a fix, test, or review round whose push is a safe change (code comments other than directive comments, `*.md` docs, test titles) uses `sonnet` at `medium`. On a cheap review round the fresh reviewer reviews the push since the last reviewed SHA against the open findings, not the full diff again. A push that changes tests gets the full reviewer. This does not apply when the security, payments, auth, and server-rendering bullet applies or in the escalation round; the highest-model sentence below resolves the conflict.
- **Escalation round:** the final fix round or final review round after earlier rounds found defects uses `fable`, `xhigh`. `fable`/`xhigh` is for escalations only: this final round, and the hardest security, payments, auth, and SSR tasks. `opus` stays the heavy default.

When several rules match, use the highest model and the highest effort among them (model order `haiku` < `sonnet` < `opus` < `fable`; effort order `low` < `medium` < `high` < `xhigh` < `max`). Every phase comment the orchestrator posts is one or two lines following `AGENTS.md` (Writing on GitHub) and records the model and effort used, for example `Plan review: APPROVE (model: opus, effort: high)`.
