# CI

How continuous integration works in this repository. The decision and its reasoning are in [ADR 0009](../decisions/0009-ci-pipeline.md); this page is the operating reference. The development cycle is in [dev-cycle.md](dev-cycle.md).

CI is one workflow, `.github/workflows/ci.yml` (name `CI`), with one job that matters for merging, `ci`. It runs once per tree that can merge: only on PRs that are ready for review, never on draft pushes, and never again on `main` after the merge. It runs no e2e tests: the full e2e suite runs on its own, once a day on `main`, in `.github/workflows/e2e.yml` (name `E2E`, [below](#affected-e2e-specs-and-the-nightly-run)). Neither `e2e.yml` nor `clean-previews.yml` is a required check; `clean-previews.yml` deletes the Convex preview of a merged or closed PR, on `main` only ([hosting, Cleanup](hosting.md#cleanup)).

## Required check

| Check name | Source         | Required |
| ---------- | -------------- | -------- |
| `ci`       | GitHub Actions | Yes      |

Nothing else is required. The workflow's other job, `warm-cache`, appears on every PR as a **skipped** check (0 billed minutes) and is not required. The `E2E` workflow never runs on a PR, so it posts no check there.

PRs run against base branches `main` and `production` (release PRs, ADR 0010). The workflow has no `paths` filter on `pull_request`, because a skipped path-filtered workflow leaves the required check `ci` pending; the `scope` step skips steps inside the job instead, so `ci` always reports.

**What each scope runs (#165).** `scope` lists changed files with `git diff --no-renames --name-only HEAD^1 HEAD` (fetch depth 2; `HEAD` is the PR merge commit, so its first parent is the base) and pipes them to `scripts/ci-scope.mjs`, which prints `scope`, `app`, `checks`, and `typecheck` for `$GITHUB_OUTPUT`. The classifier is `classify` in that script, tested by `scripts/ci-scope.test.mjs`; `scripts/ci-workflow.test.mjs` checks the step conditions below.

| Scope     | When                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Steps that run                                                                                                       |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `docs`    | Every changed file is under `docs/`, `design/`, or `.claude/`, or is a root `*.md`, and none is a `.js`/`.ts`-family file or a file a test reads (below)                                                                                                                                                                                                                                                                                                       | `release age`, install, `format:check`                                                                               |
| `tooling` | Every changed file is a non-app path: `docs/`, `design/`, `.claude/`, `.github/`, `scripts/` (with their tests and fixtures) except the scripts the build, e2e, or deploy run (below), or a root `*.md`, except the CI files `.github/workflows/ci.yml` and `scripts/ci-scope.mjs` and the docs files `test:convex` reads (below); and at least one is under `.github/` or `scripts/`, is a `.js`/`.ts`-family file, or is a file `test:scripts` reads (below) | The `docs` steps, plus `lint`, `test:scripts`, `actionlint`, and `typecheck` when a `.ts`/`.mts`/`.cts` file changed |
| `app`     | Anything else, including every change under `src/`, `convex/`, `e2e/`, `public/`, a script the build, e2e, or deploy runs (below), `.github/workflows/ci.yml`, `scripts/ci-scope.mjs`, `docs/glossary.md`, `docs/process/hosting.md`, and the root `package*.json`, `angular.json`, `netlify.toml`, `ngsw-config.json`, `tsconfig*`, and any other path not listed above; also every event but `pull_request`, and every PR into `production`                  | Every step                                                                                                           |

The `ci` workflow does not run on pushes to `main` (only `warm-cache` does), so `app` for pushes is the classifier's default, not a separate run. **Detection fails closed:** an empty file list, a path that git quotes (non-ASCII names), a path with a `.` or `..` segment, or a missing `GITHUB_EVENT_NAME` all give `app` without a warning, because the classifier chose `app`. A `git diff` that fails (the step sets `pipefail`, so a failed `git diff` fails the pipeline; `scripts/ci-workflow.test.mjs` runs the step against a repository with no parent commit), or a classifier that errors or prints nothing, also gives `app`, and only then does the step print `::warning::scope detection failed; running every check`. A rename counts both its old and new path, so moving an app file into `docs/` is an app change. A file ESLint lints (`.js`, `.mjs`, `.cjs`, `.ts`, `.mts`, `.cts`) is never `docs`, wherever it lives, so a helper script under `.claude/` gets `lint`. **Scripts the build, e2e, or deploy run are app.** `scripts/ci-scope.mjs` derives the list, so nobody keeps it by hand: every `scripts/<file>` that `package.json`, `netlify.toml`, `angular.json`, `playwright.config.ts`, or a file under `e2e/` names, plus every file those scripts import or spawn (relative imports, transitively), is `app`. Today that is `ng-convex.mjs`, `edge-bundle.mjs`, `noindex.mjs`, `sw-config-check.mjs`, `e2e.mjs`, `e2e-convex.mjs`, `e2e-lock.mjs`, `e2e-affected-local.mjs`, `e2e-affected.mjs`, `serve-ssr.mjs`, `build-icons.mjs`, `png.mjs`, `check-deploy-env.mjs`, `inline-mockup-kit.mjs`, and `clean-previews.mjs`. A referenced script counts as `app` whether or not it exists on disk, so deleting or renaming one the build still names is an app change; `./scripts/x.mjs` and `../scripts/x.mjs` count as well. A `*.test.mjs` file is tooling, because `test:scripts` is its check. **The CI files are `app`:** `.github/workflows/ci.yml`, `scripts/ci-scope.mjs`, and `scripts/e2e-affected.mjs` (and what they import) always run the full suite, because the PR's own copy of the classifier decides its scope and an edit to a build or e2e step must not merge without those steps running. This narrows #165's rule that `.github/**` is non-app, for safety. **Files a test reads are not docs.** `docs/glossary.md` and `docs/process/hosting.md` are read by `test:convex` (`convex/lib/slugs.test.ts`, `convex/lib/previewOrigin.test.ts`), so a change to either is `app`. `design/icons/`, `design/mockup-kit/`, and `design/mockups/80-app-icon.html` are read by `test:scripts` (`scripts/build-icons.test.mjs`, `scripts/global-styles.test.mjs`, `scripts/inline-mockup-kit.test.mjs`), so a change to one is `tooling`. The lists are `APP_TEST_INPUTS` and `TOOLING_TEST_INPUTS` in `scripts/ci-scope.mjs`; `scripts/ci-scope.test.mjs` fails when a Convex test reads a docs file that is not in the first list. The gap that remains: a Vitest `src/` spec, or a `scripts/` test, that starts reading another docs file is not detected until its file joins a list. The list comes from the merge commit's own files, and a PR that adds or drops a reference edits one of those files, which is itself `app`. If the list cannot be derived (a reference file is missing or names no script), the result is `app`.

**Steps of `ci`, in order:** checkout (depth 2, `persist-credentials: false`); `scope` (first, on the Node the runner image ships, before setup-node); `release age` (every npm Dependabot cooldown window equals `.npmrc` `min-release-age`; runs on every change, needs no install); setup-node (Node from `package.json` `devEngines.runtime`, npm cache automatic); `install` (`npm ci`); `format:check`; then, on `app` changes only, `audit signatures`, `test`, `test:convex`, `build`; on `app` and `tooling` changes, `lint`, `actionlint`, and (when `typecheck` is `true`) `typecheck`; then, only if every one of those passed and the scope is `app`, `chromium` (`npx playwright install --with-deps --only-shell chromium`); then `test:scripts` on `app` and `tooling` changes, last (after `chromium` so the icon re-render test finds Chromium and runs instead of skipping; it uses `!cancelled()`, so it still runs, without Chromium and skipping that one test, when an earlier check failed or the scope is `tooling`). Each check runs even when an earlier one failed, so one run reports every failure; the failing step is named in the job log and in `gh run view <id> --log-failed`. If setup-node or `install` fails, every step that needs `node_modules` is skipped, `actionlint` still runs, and `ci` fails. `ci` runs no e2e step, no Convex backend, and no `convex codegen drift` check: those run nightly in `E2E` ([E2E steps](#e2e-steps)).

**A `workflow_dispatch` run on a PR head posts a `ci` check for that SHA.** It shows in `gh pr checks` like a PR run, so a dispatch made after the last PR run becomes the latest `ci` on that head.

**A spec that reads a mockup must have a rule.** A spec opens a mockup by path, which the import graph cannot see. `findUnmappedMockupReads` in `scripts/e2e-affected.mjs` takes every file name in `design/mockups/` that a spec names and fails `test:scripts` when `selectSpecs` for that mockup does not include the spec (`e2e/harness/` in the always set does not count). It also names a spec whose text matches the word `mockups` but names no mockup file (a computed path), and any non-spec file under `e2e/` that names a mockup or matches the word. The gap that remains: a spec that names one mockup literally and builds a second path from a template; the nightly run covers it. `design/mockup-kit/` selects no spec, because the mockups inline its CSS and change in the same PR.

**Session specs are derived, not listed.** `deriveSessionSpecs` in `scripts/e2e-affected.mjs` reads `e2e/*.spec.ts` and `e2e/harness/*.spec.ts` when a changed file needs them (a sign-in, sign-up, account, or `users` file, or the home page). A spec is a session spec when it imports from `e2e/support/session.ts` (`signUp`, `otherUser`) or `e2e/support/users.ts` (`newUser`, `seedUser`), or from any other `e2e/support/` module that imports one of those, directly or through other support modules, or opens `/sign-in` or `/sign-up`; today that is `accept-invite`, `auth-session`, `create-organization`, the five `organization-*` admin specs, `organization-staff`, `sign-in-admin`, `sign-in`, `sign-up`, and `top-bar`. `signUp()` drives the real sign-up form and lands on `/app`, which queries Convex through the account page and the shell, so a change to any of those pages can break every one of these specs. A new spec that signs in is picked up without a change to the mapping. If the specs cannot be read, the result is the full suite. `scripts/e2e-affected.test.mjs` also checks the derivation against an independent scan of the real spec files: every spec that imports a sign-up helper (found by a separate scan that follows support modules the same way) must be selected by the sign-up, sign-in, account, `users`, and home-page areas.

**A file with no rule takes its importers' specs.** `scripts/e2e-affected.mjs` reads every `.ts`, `.mts`, and `.mjs` file in the repo (including `playwright.config.ts`, the root config files, and `scripts/`; not `node_modules`, `dist`, dot directories, or build output) and records which file imports which: `import … from`, `export … from`, `export * from`, `import '…'`, and `import type`, over one or many lines, with single or double quotes. A specifier resolves to the exact file, `<path>.ts`, `<path>.mts`, `<path>.d.ts`, `<path>.js`, `<path>.mjs`, `<path>/index.ts`, or the `.ts` or `.mts` file that a `.js` or `.mjs` specifier names. A changed file that no rule names then runs the union of the specs of its importers, following importers until a file with a rule. Unit specs, `scripts/*.test.mjs`, files under `testing/`, `convex/test.setup.ts`, and `convex/_generated/` are not importers.

**A hand rule takes its importers' specs.** A file under `src/app/` that a rule with specs names runs that rule's specs plus the specs selected for each file that imports it, outside the rule's own match: an importer with a rule adds that rule's specs (and, in turn, its own importers'), and an importer with no rule is traced as above, so an importer chain that ends at a root with no rule runs the full suite. Importers inside the rule's own match are followed to their importers. A shared file therefore never selects fewer specs than the pages that use it: `league/season-dates.ts` runs the organization, sport, league, and season page specs, `league/league-path.ts` runs the specs of the admin leagues page and create form, and the `admin/` files that `league/` imports (`league-division.ts`, `league-division-fields.ts`, `admin-alert.ts`, `button-classes.ts`, `field-classes.ts`, `admin-sidebar.ts`, `admin-path.ts`, `league-form.ts`) run the league management specs. Three rules opt out with `widen: false`, because a file that runs the full suite imports the file: `app.config.ts` imports `app.routes.ts`, `app.config.server.ts` imports `app.routes.server.ts`, and `saved-copies.ts` imports `offline-saved-queries.ts`. **A route table is not an importer.** `app.routes.ts` and `app.routes.server.ts` only wire a path to its page, so neither counts as an importer for the tracing or for the importer specs above. A file that only a route table imports, such as `core/auth/guards.ts` or a new guard, has no importer and runs the full suite, and does not take the route table's specs. The target of a route table's `import()` still runs the full suite when it has no rule.

**The tracing fails closed.** The full suite runs, with the reason on stderr, when:

- the changed file is not on disk (deleted), or is not a `.ts`, `.mts`, or `.mjs` file and no rule names it;
- the changed file, or a file in its importer chain, is a top-level `convex/*.ts` module with no rule (Convex loads it by file name, so no importer shows what uses it), or the target of any `import()` or `typeof import()` (a routed page, `make-auth-client.ts`, `shell-sheet.ts`), even when it also has static importers;
- the chain ends at a file with no rule and no importer (`convex/schema.ts`, `src/app/app.config.ts`, `e2e/global-setup.ts`, `playwright.config.ts`, a `scripts/` file, a root config file), or the importers only form a cycle that no rule reaches;
- any relative specifier, or any `import()` of a computed relative path, resolves to no file;
- the import graph cannot be read.

**The full suite runs** when a changed file is shared code that no importer chain places. A file under `src/app/` with no rule is traced like any other, so a shared helper that only pages with rules import (for example `src/app/core/page-meta.ts` or `src/app/ui/button/button-classes.ts`) selects those pages' specs. The full suite runs for the files under `src/app/shell/`, `src/app/core/` (auth, the Convex data adapter, the service worker), and `src/app/ui/` that `src/main*.ts`, `src/server.ts`, or a file with no rule that `import()` loads (`shell-sheet.ts`, `make-auth-client.ts`) reach, for `src/app/core/auth/guards.ts`, for `src/app/app.config*.ts` and `src/app/app.ts` (`SRC_FULL` in `scripts/e2e-affected-app.test.mjs` lists every such file under `src/app/` with its reason), and for `src/server*.ts`, `src/main*.ts`, `src/index.html`, styles and tokens, `public/`, `convex/schema.ts`, the `convex/lib/` files that `convex/testing.ts`, `convex/auth.ts`, or `convex/schema.ts` import, directly or through another `convex/lib/` file, and `convex/lib/previewOrigin.ts`, which `scripts/e2e-convex.mjs` loads with `import()` (`CONVEX_LIB_FULL` in `scripts/e2e-affected-tracing.test.mjs` lists them with the reason), `convex/auth*.ts`, `convex/http.ts`, `convex/testing.ts`, `convex/health.ts`, every other top-level `convex/*.ts` module with no rule, every file under `convex/_generated/` except the three type files, `e2e/global-setup.ts` and the support files it imports, `playwright.config.ts` and the support files it imports (`viewport-agnostic.ts`, `raw-http.ts`), `scripts/e2e.mjs`, `scripts/e2e-convex.mjs`, `package*.json`, `angular.json`, `netlify.toml`, `tsconfig*`, `.github/workflows/ci.yml`, `scripts/ci-scope.mjs`, the other scripts the build and e2e run, and any other path that is not a `.ts`, `.mts`, or `.mjs` file. It also runs for every event but a `pull_request` into `main` (a `workflow_dispatch`, a `schedule`, a release PR into `production`), for an empty or unreadable file list, for a path that is not plainly relative, and when the selection script fails or prints nothing.

`scripts/e2e-affected.test.mjs` pins the mapping, every full-suite fallback, and that each filter selects exactly the spec file it names. It also fails when a spec file exists that no rule maps, until the spec is mapped or added to its `FULL_SUITE_ONLY` list (today `screenshot`, which runs on a change to itself and nightly; `cache-key` also runs for a change to the public league page, the public organization page, or `convex/organizations`, `leagues`, or `seasons`, #127). `scripts/e2e-affected-tracing.test.mjs` covers the tracing against fixture repos (each parse and resolution case, cycles, dynamic imports, not-importers, roots, and the fail-closed cases), the rules against the real repo, the public-page finder and its query list, `CONVEX_LIB_FULL`, and a replay of two earlier public-page PRs. `scripts/e2e-affected-app.test.mjs` covers the rules for `src/app`: the league management page finder and the 10 specs it must find, the check that every hand rule selects at least the specs of each importer outside its match (its exception list is empty today), `ROUTE_SPECS` against every `path:` and `canActivate` in the route table, the offline query groups against the `*_PAGE_QUERIES` constants, `SRC_FULL`, and a replay of three earlier PRs. A new route, or a new directory under `src/app/` whose files would run the full suite, adds its rule in the same PR, because the tests fail until it does. The nightly full run is the net for a spec that the tracing misses. `scripts/e2e-workflow.test.mjs` runs the shell of the `nightly-gate` and `nightly-issue` steps against a fake `gh`, and checks the shape of `e2e.yml`.

**Quiet nights.** A night on which nothing merged would repeat the last green night, so job `nightly-gate` in `e2e.yml` (scheduled runs only, `permissions: actions: read`, no checkout, the workflow `GITHUB_TOKEN`) asks `gh run list --workflow e2e.yml --event schedule --status success --branch main --limit 1` for the commit the last successful scheduled run tested. When that equals the commit tonight's run is for, it prints a notice and job `e2e` is skipped (0 billed minutes, no issue). A failed or empty lookup, a moved `main`, or no green night yet runs the full suite. A night after a failed night runs again, because no newer night succeeded. `e2e` needs the gate and uses `!cancelled()` with `needs.nightly-gate.outputs.skip != 'true'`, so a skipped gate (a dispatch) and a failed gate do not skip `e2e`.

**The nightly run.** `e2e.yml` has a `schedule` trigger (`17 3 * * *`, UTC) and `workflow_dispatch`, and no PR or push trigger. A schedule runs only on the default branch. Its job `e2e` runs checkout, setup-node, `npm ci`, and the [E2E steps](#e2e-steps), with the full suite in both Chromium projects. When `e2e` fails on a scheduled run, job `nightly-issue` runs with `permissions: issues: write` (the workflow's `GITHUB_TOKEN`, no other secret, no checkout, no action). The `e2e failures` step reads Playwright's JSON report (`test-results/results.json`) with `scripts/e2e-failures.mjs` and passes the failing tests (at most 30, as `project: file:line: title`) as a job output. `nightly-issue` then opens one `type:bug` issue titled `Nightly e2e failed on main`, or comments on it when it is already open, with the failing tests and a link to the run. When a step before e2e failed, the issue says no failing test was recorded and links the run. Each failing test is wrapped in backticks, so an `@name` or `#123` in a title does not mention or link. The issue is created with `type:bug` and `status:ready`: it is an urgent regression on `main`, so it skips planning and plan review on purpose and the orchestrator triages it directly; closing it makes the next failure open a new one. `scripts/e2e-workflow.test.mjs` checks the workflow's triggers, jobs, permissions, and the gate and issue scripts.

## Merge procedure

The orchestrator merges one PR at a time (dev cycle Phase 7):

1. If the PR branch is behind `main`, update it **while it is still a draft**: `gh pr update-branch <n>`. No CI runs. A clean update (no conflicts, none of the PR's own files changed) keeps the tester's `PASS` and the reviewer's `APPROVE`. A conflicted update sends the PR back to the implementer, and Phases 5 and 6 run again. If this page and [dev-cycle.md](dev-cycle.md) Phase 7 differ, dev-cycle.md governs.
2. Mark it ready: `gh pr ready <n>`. This starts the one `ci` run.
3. Read the head SHA (`gh pr view <n> --json headRefOid`), then wait until `gh pr checks <n> --json name,bucket,workflow` shows `ci` from workflow `CI` with `bucket` `pass`. **`skipping` is not a pass:** it is the draft-time skip.
4. Merge: `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>`. If another PR merged meanwhile, GitHub refuses the merge (strict rule); go back to step 1.
5. If `ci` fails, convert the PR back to draft (`gh pr ready <n> --undo`) and return it to the implementer, so fix iterations cost nothing.

**Gate PRs** (ADRs) are opened ready, because the owner reads and merges them. They are docs-only, so each push costs 1 to 2 minutes. If one is behind `main`, the owner presses "Update branch" (or the orchestrator runs step 1) before merging.

**Dependabot PRs** are opened ready by Dependabot and follow steps 1, 3, and 4. Minor and patch PRs need `ci` green on an up-to-date head and a PR reviewer `APPROVE` (release notes read, `allowScripts` changes justified); there is no linked issue and no tester phase. An **npm major** gets `gate:technology` and waits for the owner. A GitHub-owned **action major** needs no gate; the reviewer reads its release notes. Every npm cooldown window in `.github/dependabot.yml` (`default-days`, `semver-patch-days`, `semver-minor-days`, `semver-major-days`) equals `.npmrc` `min-release-age` (3 days), so npm majors are proposed after 3 days, not 7, and Dependabot resolves the lockfile under the same release-age rule as local installs; the `release age` step in `ci` fails when any window differs or is missing ([ADR 0003](../decisions/0003-package-manager-and-node.md) and [ADR 0009](../decisions/0009-ci-pipeline.md) amendments, #47). TypeScript majors are ignored until the repository moves to the Angular major that supports TypeScript 7; the rule uses `update-types` only, so TypeScript security updates are unaffected.

Agents never push to `main` directly.

**How each figure is read:**

- **Per run:** sum, over the run's jobs, of `completedAt − startedAt` from `gh run view <id> --json jobs`, each job rounded up to a whole minute (always available). The `billable` value from `gh api repos/jasonbryan/omni-league/actions/runs/<id>/timing` is recorded next to it only when it is non-empty and non-zero. GitHub documents that endpoint as "in the process of closing down", so it is never the only source.
- **A skipped run:** `gh run view <id> --json jobs` shows the job with conclusion `skipped`, no steps, and no runner. That is the 0-minute proof.
- **The monthly total:** the account's Billing and plans usage page, <https://github.com/settings/billing/usage>, filtered to Actions for the current month. Per-run figures cannot give a monthly total.

**Budget rule:** if a month passes **1,500 minutes** (50% of Pro's 3,000), the orchestrator reports it to the owner with the top workflows from the usage page. GitHub's included-usage alerts also email the owner.
