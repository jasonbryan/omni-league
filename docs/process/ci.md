# CI

How continuous integration works in this repository. The decision and its reasoning are in [ADR 0009](../decisions/0009-ci-pipeline.md); this page is the operating reference. The development cycle is in [dev-cycle.md](dev-cycle.md).

CI is one workflow, `.github/workflows/ci.yml` (name `CI`), with one job that matters for merging, job id `checks`, which is named `ci` when it runs the full suite. The full `ci` runs once per tree that can merge: when the orchestrator adds `ready-to-merge` to an up-to-date PR, and again on any later push. Draft pushes run nothing. Pushes to a ready PR run only the fast checks, without e2e, and create no `ci`. It never runs again on `main` after the merge, except for a nightly full run on `main` ([below](#affected-e2e-specs-and-the-nightly-run)), which reuses the same job. The owner's decision and the alternatives are in [ADR 0009, "Amendment: fast checks on every push, e2e once at merge, nightly once per commit"](../decisions/0009-ci-pipeline.md). A second workflow, `clean-previews.yml`, is not CI: it deletes the Convex preview of a merged or closed PR, on `main` only ([hosting, Cleanup](hosting.md#cleanup)) and is not a required check.

## Required check

| Check name | Source         | Required |
| ---------- | -------------- | -------- |
| `ci`       | GitHub Actions | Yes      |

Nothing else is required. The workflow's other jobs, `warm-cache`, `nightly-gate`, and `nightly-issue`, appear on every PR as **skipped** checks (0 billed minutes) and are not required. The fast job `checks` is not required either: a green `checks` is never a merge condition, only a full `ci` is.

**The job is named `ci` only where it is a pass that means something.** A job skipped by `if` reports success to the ruleset, so a skipped job named `ci` on a PR head would satisfy the required check without a single test. Job id `checks` has the name `ci` on a nightly run the gate did not skip, a dispatch, a `labeled` event whose label is `ready-to-merge`, `gate:technology`, or `gate:production`, and a non-label event on a PR that has one of those labels or targets `production`. Every other path, skipped or fast, is named `checks`, a gated nightly run included, so no skipped job is named `ci` on any commit: the tip of `main` is also the head of a release PR into `production`, which requires `ci`, and a skipped `ci` there would hide that PR's own failed `ci`. The job-level variable `FULL_RUN` repeats the same condition (a job name cannot read `env`), and `scripts/ci-workflow.test.mjs` checks name, `if`, `FULL_RUN`, and the concurrency group for every event shape.

**Concurrency.** The group is `ci-<PR number>` with `cancel-in-progress`, so a newer push or a trigger label cancels the run before it for the same PR. A `labeled` event whose label is outside the trigger set uses `run-<run_id>`, its own group, so a `type:` label added while the full `ci` runs cancels nothing.

PRs run against base branches `main` and `production` (release PRs, ADR 0010). The workflow has no `paths` filter on `pull_request`; the `scope` step skips steps inside the job instead, so a `ci` that runs always reports. A PR without `ready-to-merge` has no `ci` on its head on purpose: the required check is missing, so the ruleset blocks the merge until the orchestrator labels the PR.

**What each scope runs (#165).** `scope` lists changed files with `git diff --no-renames --name-only HEAD^1 HEAD` (fetch depth 2; `HEAD` is the PR merge commit, so its first parent is the base) and pipes them to `scripts/ci-scope.mjs`, which prints `scope`, `app`, `checks`, and `typecheck` for `$GITHUB_OUTPUT`. The classifier is `classify` in that script, tested by `scripts/ci-scope.test.mjs`; `scripts/ci-workflow.test.mjs` checks the step conditions below.

| Scope     | When                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Steps that run                                                                                                       |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `docs`    | Every changed file is under `docs/`, `design/`, or `.claude/`, or is a root `*.md`, and none is a `.js`/`.ts`-family file or a file a test reads (below)                                                                                                                                                                                                                                                                                                       | `release age`, install, `format:check`                                                                               |
| `tooling` | Every changed file is a non-app path: `docs/`, `design/`, `.claude/`, `.github/`, `scripts/` (with their tests and fixtures) except the scripts the build, e2e, or deploy run (below), or a root `*.md`, except the CI files `.github/workflows/ci.yml` and `scripts/ci-scope.mjs` and the docs files `test:convex` reads (below); and at least one is under `.github/` or `scripts/`, is a `.js`/`.ts`-family file, or is a file `test:scripts` reads (below) | The `docs` steps, plus `lint`, `test:scripts`, `actionlint`, and `typecheck` when a `.ts`/`.mts`/`.cts` file changed |
| `app`     | Anything else, including every change under `src/`, `convex/`, `e2e/`, `public/`, a script the build, e2e, or deploy runs (below), `.github/workflows/ci.yml`, `scripts/ci-scope.mjs`, `docs/glossary.md`, `docs/process/hosting.md`, and the root `package*.json`, `angular.json`, `netlify.toml`, `ngsw-config.json`, `tsconfig*`, and any other path not listed above; also every event but `pull_request`, and every PR into `production`                  | Every step                                                                                                           |

The `ci` workflow does not run on pushes to `main` (only `warm-cache` does), so `app` for pushes is the classifier's default, not a separate run. **Detection fails closed:** an empty file list, a path that git quotes (non-ASCII names), a path with a `.` or `..` segment, or a missing `GITHUB_EVENT_NAME` all give `app` without a warning, because the classifier chose `app`. A `git diff` that fails (the step sets `pipefail`, so a failed `git diff` fails the pipeline; `scripts/ci-workflow.test.mjs` runs the step against a repository with no parent commit), or a classifier that errors or prints nothing, also gives `app`, and only then does the step print `::warning::scope detection failed; running every check`. A rename counts both its old and new path, so moving an app file into `docs/` is an app change. A file ESLint lints (`.js`, `.mjs`, `.cjs`, `.ts`, `.mts`, `.cts`) is never `docs`, wherever it lives, so a helper script under `.claude/` gets `lint`. **Scripts the build, e2e, or deploy run are app.** `scripts/ci-scope.mjs` derives the list, so nobody keeps it by hand: every `scripts/<file>` that `package.json`, `netlify.toml`, `angular.json`, `playwright.config.ts`, or a file under `e2e/` names, plus every file those scripts import or spawn (relative imports, transitively), is `app`. Today that is `ng-convex.mjs`, `edge-bundle.mjs`, `noindex.mjs`, `sw-config-check.mjs`, `e2e.mjs`, `e2e-convex.mjs`, `e2e-lock.mjs`, `e2e-affected-local.mjs`, `e2e-affected.mjs`, `serve-ssr.mjs`, `build-icons.mjs`, `png.mjs`, `check-deploy-env.mjs`, `inline-mockup-kit.mjs`, and `clean-previews.mjs`. A referenced script counts as `app` whether or not it exists on disk, so deleting or renaming one the build still names is an app change; `./scripts/x.mjs` and `../scripts/x.mjs` count as well. A `*.test.mjs` file is tooling, because `test:scripts` is its check. **The CI files are `app`:** `.github/workflows/ci.yml`, `scripts/ci-scope.mjs`, and `scripts/e2e-affected.mjs` (and what they import) always run the full suite, because the PR's own copy of the classifier decides its scope and an edit to a build or e2e step must not merge without those steps running. This narrows #165's rule that `.github/**` is non-app, for safety. **Files a test reads are not docs.** `docs/glossary.md` and `docs/process/hosting.md` are read by `test:convex` (`convex/lib/slugs.test.ts`, `convex/lib/previewOrigin.test.ts`), so a change to either is `app`. `design/icons/`, `design/mockup-kit/`, and `design/mockups/80-app-icon.html` are read by `test:scripts` (`scripts/build-icons.test.mjs`, `scripts/global-styles.test.mjs`, `scripts/inline-mockup-kit.test.mjs`), so a change to one is `tooling`. The lists are `APP_TEST_INPUTS` and `TOOLING_TEST_INPUTS` in `scripts/ci-scope.mjs`; `scripts/ci-scope.test.mjs` fails when a Convex test reads a docs file that is not in the first list. The gap that remains: a Vitest `src/` spec, or a `scripts/` test, that starts reading another docs file is not detected until its file joins a list. The list comes from the merge commit's own files, and a PR that adds or drops a reference edits one of those files, which is itself `app`. If the list cannot be derived (a reference file is missing or names no script), the result is `app`.

**Steps of the job, in order:** checkout (depth 2, `persist-credentials: false`); `merge ref` (full `pull_request` runs only: fails with `stale merge ref` unless the checked-out merge commit's second parent, `HEAD^2`, is `github.event.pull_request.head.sha`; GitHub recomputes `refs/pull/<n>/merge` after `update-branch` without a delay guarantee, so a label added seconds later can otherwise test the old head while `ci` attaches to the new one; on failure setup-node and everything after it are skipped); `scope` (on the Node the runner image ships, before setup-node); `e2e specs` (same Node, `app` scope in a full run only: which e2e specs run, see [below](#affected-e2e-specs-and-the-nightly-run)); `release age` (every npm Dependabot cooldown window equals `.npmrc` `min-release-age`; runs on every change, needs no install); setup-node (Node from `package.json` `devEngines.runtime`, npm cache automatic); `install` (`npm ci`); `format:check`; then, on `app` changes only, `audit signatures`, `test`, `test:convex`, `build`; on `app` and `tooling` changes, `lint`, `actionlint`, and (when `typecheck` is `true`) `typecheck`; then, only if every one of those passed, the scope is `app`, and the run is a full run, `e2e browsers`; then `test:scripts` on `app` and `tooling` changes (after `e2e browsers` so the icon re-render test finds Chromium and runs instead of skipping; it uses `!cancelled()`, so it still runs, without Chromium and skipping that one test, when an earlier check failed or the scope is `tooling`); then, only if every step before it passed, `e2e backend`, `convex codegen drift`, `e2e` (full run only), `e2e failures` (nightly runs only), and `e2e report` (see [E2E steps](#e2e-steps)). A **fast run** (`FULL_RUN` is `0`) skips `merge ref`, `e2e specs`, `e2e browsers`, and `e2e`, so `test:scripts` runs without Chromium and skips the icon re-render test, as it does for `tooling` scope. Each check runs even when an earlier one failed, so one run reports every failure; the failing step is named in the job log and in `gh run view <id> --log-failed`. If setup-node or `install` fails, every step that needs `node_modules` is skipped, `actionlint` still runs, and `ci` fails.

**A `workflow_dispatch` run on a PR head posts a `ci` check for that SHA.** It shows in `gh pr checks` like a PR run, so a dispatch made after the last PR run becomes the latest `ci` on that head.

## Affected e2e specs and the nightly run

Owner decision, 2026-10-12 ([#186](https://github.com/jasonbryan/omni-league/issues/186), [ADR 0009, "Amendment: affected e2e specs on PRs, full suite nightly"](../decisions/0009-ci-pipeline.md)): a PR's `ci` runs the e2e specs its change can affect, and the whole suite runs once a night on `main`. Since 2026-10-14 ([ADR 0009, "Amendment: fast checks on every push, e2e once at merge, nightly once per commit"](../decisions/0009-ci-pipeline.md)) that `ci` runs once, when the PR gets `ready-to-merge`; a push to a ready PR runs the fast checks only. Locally, testers and implementers run the same selection with `npm run e2e:affected` ([dev cycle, Test](dev-cycle.md#5-test)). The required check stays `ci`.

**Which specs a PR runs.** The `e2e specs` step (the step after `scope`, `app` scope only) pipes the same `git diff --no-renames --name-only HEAD^1 HEAD` to `scripts/e2e-affected.mjs`, which prints `e2e_scope` (`affected` or `full`) and `e2e_specs` (space-separated Playwright file filters) for `$GITHUB_OUTPUT`. The `e2e` step runs `npm run e2e -- <filters>` only when `e2e_scope` is `affected`; any other value, including a skipped or failed `e2e specs` step, runs every spec. The mapping is `AREAS` in `scripts/e2e-affected.mjs`: the first rule that matches a file decides it, and the specs of all changed files are united.

**Session specs are derived, not listed.** `deriveSessionSpecs` in `scripts/e2e-affected.mjs` reads `e2e/*.spec.ts` and `e2e/harness/*.spec.ts` when a changed file needs them (a sign-in, sign-up, account, or `users` file, or the home page). A spec is a session spec when it imports from `e2e/support/session.ts` (`signUp`, `otherUser`) or `e2e/support/users.ts` (`newUser`, `seedUser`), or from any other `e2e/support/` module that imports one of those, directly or through other support modules, or opens `/sign-in` or `/sign-up`; today that is `accept-invite`, `auth-session`, `create-organization`, the five `organization-*` admin specs, `organization-staff`, `sign-in-admin`, `sign-in`, `sign-up`, and `top-bar`. `signUp()` drives the real sign-up form and lands on `/app`, which queries Convex through the account page and the shell, so a change to any of those pages can break every one of these specs. A new spec that signs in is picked up without a change to the mapping. If the specs cannot be read, the result is the full suite. `scripts/e2e-affected.test.mjs` also checks the derivation against an independent scan of the real spec files: every spec that imports a sign-up helper (found by a separate scan that follows support modules the same way) must be selected by the sign-up, sign-in, account, `users`, and home-page areas.

**The full suite runs** when a changed file is shared code or has no rule, so a new area runs everything until someone maps it: `src/app/shell/`, `src/app/core/` (auth, the Convex data adapter, the service worker), `src/app/ui/`, `src/app/app.*.ts`, `src/server*.ts`, `src/main*.ts`, `src/index.html`, styles and tokens, `public/`, `convex/schema.ts`, `convex/lib/`, `convex/auth*.ts`, `convex/http.ts`, `convex/testing.ts`, `convex/_generated/`, `e2e/support/`, `e2e/global-setup.ts`, `playwright.config.ts`, `package*.json`, `angular.json`, `netlify.toml`, `tsconfig*`, `.github/workflows/ci.yml`, `scripts/ci-scope.mjs`, `scripts/e2e-affected.mjs`, the other scripts the build and e2e run, and any path not named above. It also runs for every event but a `pull_request` into `main` (a `workflow_dispatch`, a `schedule`, a release PR into `production`), for an empty or unreadable file list, for a path that is not plainly relative, and when the selection script fails or prints nothing (the step then warns `e2e spec selection failed; running the full suite`).

`scripts/e2e-affected.test.mjs` pins the mapping, every full-suite fallback, and that each filter selects exactly the spec file it names. It also fails when a spec file exists that no rule maps, until the spec is mapped or added to its `FULL_SUITE_ONLY` list (today `convex-backend` and `screenshot`, which run on a change to themselves, on a shared change, and nightly; `cache-key` also runs for a change to the public league page, the public organization page, or `convex/organizations`, `leagues`, or `seasons`, #127). `scripts/ci-e2e-selection-workflow.test.mjs` runs the shell of the `e2e specs`, `e2e`, and `nightly-issue` steps against scratch repositories, a fake `npm`, and a fake `gh`, and checks the workflow's shape.

**Quiet nights.** A night on which nothing merged would repeat the last tested night, so job `nightly-gate` (scheduled runs only, `permissions: actions: read`, no checkout, the workflow `GITHUB_TOKEN`) lists the last 10 completed scheduled runs of `ci.yml` on `main`, newest first (`gh run list --workflow ci.yml --event schedule --branch main --status completed --limit 10`), and reads each one's jobs (`gh run view <id> --json jobs`) until it finds a **tested** night. A night is tested when its job `ci` concluded `success` or `failure`, or when `nightly-gate` succeeded and the job concluded `skipped` (a gate skip; the skipped job is named `checks`, and `ci` is read too for runs made before that rename). A night with `startup_failure`, a `cancelled` run (its own conclusion, even when its jobs read as a gate skip), a `cancelled` `ci`, or no `ci` job tested nothing, and the gate looks at the one before it. When the newest tested night is for the commit tonight's run is for, the gate prints a notice and the job is skipped (it concludes `skipped`, is named `checks`, 0 billed minutes, no issue). A moved `main`, no tested night in the last 10, or any failed lookup runs the full suite. A night after a failed night is skipped when `main` has not moved: the failure already opened or updated the `type:bug` issue, and a rerun on the same commit would repeat it. While Actions minutes are exhausted, scheduled runs fail at startup, count as untested, and cannot make an untested `main` look tested. The job needs the gate and uses `!cancelled()` with `needs.nightly-gate.outputs.skip != 'true'`, so a skipped gate (every event but a schedule: PRs, dispatches, pushes) and a failed gate do not skip it. `scripts/ci-e2e-selection-workflow.test.mjs` runs the gate's shell against a fake `gh` that applies the workflow's own `--jq` filters with `jq`.

**The nightly run.** `ci.yml` has a `schedule` trigger (`17 3 * * *`, UTC). A schedule runs only on the default branch, so it never runs on a PR branch. It is the `ci` job itself, with every step and the full suite in both Chromium projects (`webkit-mobile` stays release-only), so no step is copied; a reusable workflow would rename the required check to `ci / ci`. When `ci` fails on a scheduled run, job `nightly-issue` runs with `permissions: issues: write` (the workflow's `GITHUB_TOKEN`, no other secret, no checkout, no action). The `e2e failures` step reads Playwright's JSON report (`test-results/results.json`) with `scripts/e2e-failures.mjs` and passes the failing tests (at most 30, as `project: file:line: title`) as a job output. `nightly-issue` then opens one `type:bug` issue titled `Nightly e2e failed on main`, or comments on it when it is already open, with the failing tests and a link to the run. When a step before e2e failed, the issue says no failing test was recorded and links the run. Each failing test is wrapped in backticks, so an `@name` or `#123` in a title does not mention or link. The issue is created with `type:bug` and `status:ready`: it is an urgent regression on `main`, so it skips planning and plan review on purpose and the orchestrator triages it directly; closing it makes the next failure open a new one.

## E2E steps

The e2e harness ([ADR 0005](../decisions/0005-e2e-and-accessibility-testing.md), amended by ADR 0009; usage in the [README](../../README.md#e2e-tests)) runs as the last steps of the `ci` job: no separate job and no new check name. `e2e backend` has `if: ${{ success() && steps.scope.outputs.app == 'true' }}` and `e2e browsers` adds `&& env.FULL_RUN == '1'`, so any earlier failure, or a `docs` or `tooling` PR, skips them, and a fast run skips `e2e browsers`; a `test:scripts` failure, which sits between them, skips `e2e backend` and everything after it. `convex codegen drift` runs whenever `e2e backend` succeeded, and `e2e` does too in a full run, so a drift failure and an e2e failure are reported by the same run.

| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `e2e browsers`         | `npx playwright install --with-deps --only-shell chromium` (the Playwright config sets no `channel`, so headless runs use the headless shell); also `npx playwright install --with-deps webkit` when `E2E_WEBKIT` is `1`. No browser cache.                                                                                                                                                                                                                                                          |
| `e2e specs`            | `node scripts/e2e-affected.mjs` on the PR's changed files (see [above](#affected-e2e-specs-and-the-nightly-run)); `app` scope only, right after `scope`.                                                                                                                                                                                                                                                                                                                                             |

| `convex codegen drift` | `git diff --exit-code convex/_generated` and `git status --porcelain --untracked-files=all -- convex/_generated` (ADR 0009): fails when the committed generated files differ from what codegen just wrote, or codegen wrote a file that is not committed. The workflow opens nothing and keeps read-only permissions.

`vitest.serial.config.mts` is not used by `ci`: it backs the local `npm run test:serial` (one Vitest worker, [dev cycle, Implement](dev-cycle.md#4-implement)) and is passed through the accepted `@angular/build:unit-test` builder's `--runner-config` option, so it is not drift from the configs in [ADR 0004](../decisions/0004-unit-and-convex-test-runners.md).

## Merge procedure

The orchestrator merges one PR at a time (dev cycle Phase 7):

1. If the PR branch is behind `main`, update it **while it is still a draft**: `gh pr update-branch <n>`. No CI runs. A clean update (no conflicts, none of the PR's own files changed) keeps the tester's `PASS` and the reviewer's `APPROVE`. A conflicted update sends the PR back to the implementer, and Phases 5 and 6 run again. If this page and [dev-cycle.md](dev-cycle.md) Phase 7 differ, dev-cycle.md governs.
2. Mark it ready: `gh pr ready <n>`. This runs nothing.
3. Add the label: `gh pr edit <n> --add-label ready-to-merge`, then read the head SHA (`gh pr view <n> --json headRefOid`). The label starts the one full `ci` run on the merge of the up-to-date head.
4. Wait until `gh pr checks <n> --json name,bucket,workflow` shows `ci` from workflow `CI` with `bucket` `pass`. **`skipping` is not a pass.** A `checks` entry is never a pass.
5. Merge: `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>`. If another PR merged meanwhile, GitHub refuses the merge (strict rule); go to step 7.
6. If `ci` was cancelled, or failed with the error `stale merge ref` (the `merge ref` step, above), remove the label (`gh pr edit <n> --remove-label ready-to-merge`) and add it again. The PR is sound; GitHub had not yet recomputed its merge ref.
7. If `ci` fails, or `main` moved before the merge, remove the label and convert the PR back to draft (`gh pr ready <n> --undo`), then update it (step 1) or return it to the implementer. Remove the label first: a draft that still has it runs the full `ci` on every push.

**Gate PRs** (ADRs) are opened ready, because the owner reads and merges them. A gate label starts `ci` without `ready-to-merge`, on draft and ready PRs alike, and on every later push. They are docs-only, so each run costs 1 to 2 minutes. If one is behind `main`, the owner presses "Update branch" (or the orchestrator runs step 1) before merging.

**Dependabot PRs** are opened ready by Dependabot, so each push runs the fast `checks`, and step 1 (`update-branch`) is not free: it runs a fast `checks` of about 5 minutes. They follow steps 1, 3, 4, and 5 and get `ready-to-merge` like any PR. Minor and patch PRs need `ci` green on an up-to-date head and a PR reviewer `APPROVE` (release notes read, `allowScripts` changes justified); there is no linked issue and no tester phase. An **npm major** gets `gate:technology` and waits for the owner. A GitHub-owned **action major** needs no gate; the reviewer reads its release notes. Every npm cooldown window in `.github/dependabot.yml` (`default-days`, `semver-patch-days`, `semver-minor-days`, `semver-major-days`) equals `.npmrc` `min-release-age` (3 days), so npm majors are proposed after 3 days, not 7, and Dependabot resolves the lockfile under the same release-age rule as local installs; the `release age` step fails when any window differs or is missing ([ADR 0003](../decisions/0003-package-manager-and-node.md) and [ADR 0009](../decisions/0009-ci-pipeline.md) amendments, #47). TypeScript majors are ignored until the repository moves to the Angular major that supports TypeScript 7; the rule uses `update-types` only, so TypeScript security updates are unaffected.

Agents never push to `main` directly.

- **A skipped run:** `gh run view <id> --json jobs` shows the job with conclusion `skipped`, no steps, and no runner. That is the 0-minute proof.
- **The monthly total:** the account's Billing and plans usage page, <https://github.com/settings/billing/usage>, filtered to Actions for the current month. Per-run figures cannot give a monthly total.
